# V1.2 — Authoritative Omnisearch

One search box now finds cards, numbered Comprehensive Rules, and the official
glossary. Rules have compact labeled result rows, dedicated authoritative text
views, parent/subrule navigation, and tappable validated source references. Back
restores the query and selection; New search starts a fresh query. Recently viewed
still holds only five cards. Card rendering, symbols, normalization, ranking,
transformation and the checked-in card dataset are unchanged.

This implementation is a **labeled rules preview**, explicitly selected by the
user. It has not been deployed or pushed by this task.

## Architecture and routing

The existing card-name index is constructed once, on the existing startup path.
A separate worker starts after card readiness, fetches the canonical rules corpus,
prebuilt BM25 index and release metadata, verifies their hashes, and constructs
small lookup maps. The worker never receives or rebuilds a card index. Queries
return compact IDs/kinds/keys/titles; a detail request returns just its document
and related navigation metadata. Stale responses cannot replace newer queries.
Card results remain usable while rules load or fail.

Routing remains the research split/prebuilt policy: explicit rule number; exact
card/face name; exact glossary or section title; up to four useful card matches
for short queries; rules relevance; remaining cards. UI allows 20 results rather
than the research harness's 10, preserving the existing card result capacity.
The first ten rankings match the baseline on **all 66 frozen queries**. The set
is small and author-written, not independent evidence of question-answer accuracy.
Top-five primary-destination success remains **83.3%**, with **65% for prose and
0/4 colloquial questions**. No summaries, generated answers, confidence labels,
inferred links or card-interaction reasoning are added.

`src/search.ts`, `src/detail.ts`, `src/recent.ts`, `scripts/build_data.py` and
`public/data/cards.json` have no changes. Card search results preserve their
relative order; a glossary exact match can precede non-exact cards.

## Source identity and effective-date policy

- Publisher: Wizards of the Coast; English Comprehensive Rules, including glossary.
- Discovery: https://magic.wizards.com/en/rules
- Exact source: https://media.wizards.com/2026/downloads/MagicCompRules%2020260925.txt
- Retrieved: **2026-09-20T16:17:03.713523+00:00**; independently redownloaded and verified during research.
- Effective: **2026-09-25**; production build as of **2026-09-22 UTC**, status `future`.
- Original SHA-256: `8d860e451f20f38865b725b42d82feb714c725373dd8f3b32b8652b3eeb070ca`.
- Parser **1.0.1**, corpus schema **1**.
- 4,062 documents: 3,165 rules/subrules, 156 sections, 741 glossary entries.

The selected mode is `preview` in `data-sources/rules/selection.json`, bound to that
specific source hash. Preview appears in result labels and detail views, with the
effective date. It **does not silently become an effective release when the date
arrives**; that requires an explicit selection change and rebuild. An `effective`
build fails if the source date is still future. Runtime also refuses premature
`effective` releases, subject to the device's clock. No older rules were guessed.
No current-effective rules corpus was available to replace or retain in V1.1.
Card date and rules effective/preview status are displayed separately.

Rule URLs bind `(source SHA-256, document ID)`. Links to another edition show a
snapshot mismatch instead of silently redirecting the rule number into a new
meaning. Expanded source information includes the original URL, retrieval time,
build date/status, parser/schema versions, source lines and full snapshot hash.
Derived headings are identified as contextual metadata; bodies are source text.

## Promoted code and update procedure

The validated parser now lives at `scripts/rules_parser.py`. Research keeps its
original CLI using that implementation. BM25 scoring/tokenization now lives at
`src/rules-search.ts`; research preparation transpiles it for its browser harness.
There is one parser and one BM25 algorithm, not parallel production/research copies.
The frozen evaluation judgments were not edited. Original source bytes and credits
are retained in `data-sources/rules/`; only runtime artifacts enter `public/data/`.

1. Fetch the actually linked official source into a **new directory**:
   `python3 scripts/fetch_rules.py --output /tmp/mtg-rules-new`.
2. Review the effective date, source changes, parser audit and references. Do not
   overwrite the selected source merely because a newer download exists.
3. For a future snapshot, retain the current effective release. If intentionally
   previewing it, explicitly choose `preview` and label it; do not call it current.
4. To select a reviewed snapshot, replace `data-sources/rules/comprehensive-rules.txt`
   and `provenance.json` together, and update `selection.json` with its exact hash,
   mode and decision. Use `effective` only on/after the effective date.
5. Run `npm run rules`, `npm test`, `npm run test:research`, `npm run build`,
   and `node --experimental-strip-types scripts/measure-v12.ts`. Review renamed
   rule IDs/judgments deliberately; never drop difficult queries to improve scores.
6. Deploy the complete `dist/` output through the existing Pages workflow. It
   refreshes cards but **does not automatically select newly published rules**.
   A failed source-policy check or build prevents deployment.

The downloader refuses unexpected source hosts and nonempty output directories.
The builder refuses source/provenance/selection hash disagreement. Runtime checks
both artifact hashes, corpus/source identity, index version, document count and
source metadata before announcing readiness. Source order, IDs, parents, glossary,
subrules and conservative cross-references retain parser audit coverage.

An offline defect was found and fixed: `Vary: Origin` from the preview server could
make module requests miss precached files. Hash-verified static cache lookups now
ignore header variation; a regression test and server-off Chromium reload pass.

No new source parsing defect was discovered beyond the comma-reference fix already
made in research parser 1.0.1. Zero unresolved recognized references does not mean
all semantic relationships or ranges have been extracted. The promoted scorer uses
an own-property check for postings so words resembling inherited object properties
cannot be mistaken for posting lists; this does not change the evaluation rankings.

## Verification and offline behavior

Production tests: 33 Node tests and 5 Python tests. Research tests: 2 Node and
3 Python tests. TypeScript checking and Vite/service-worker build pass. Frozen
66-query comparison reports no top-ten differences. For later card-data refreshes,
tests compare production/research routing on the same updated inputs as well, so
legitimate upstream popularity changes are not mistaken for routing changes.

The existing atomic service worker now caches **and SHA-verifies every asset**
before installation succeeds. An interrupted download, missing asset, or bytes
from another deploy deletes the incomplete new cache and leaves the prior complete
cache intact. Updates still wait for the existing Reload action. Corpus/index
integrity also has a worker-level check. Simulation tests cover rollback after
interruption and HTTP-success/wrong-index bytes, fresh-worker offline shell/cards/
rulings/fonts/rules/glossary/reference navigation, and activation cleanup.

Observed browser checks:

- In-app browser, 375 px: glossary intent, preview labels, rule/child links, Back
  through references to the saved query, Sol Ring detail, New search and card-only
  recents. Desktop layout and dark theme checked separately.
- Safari with the preview server stopped: cold reload restored `ward`; glossary
  detail → rule 702.21 → subrule 702.21a worked; New search → Necropotence showed
  Oracle text, symbols and all four official rulings from cache.
- Chromium in-app browser, after fixing `Vary: Origin` matching: server-off cold
  reload restored `ward`, glossary → rule navigation worked, and New search →
  Sol Ring opened cached card details. Both browser engines now pass the real-cache
  check. Physical Android installation/update checks remain manual.

## Android installed-PWA acceptance checklist

1. On the deployed **HTTPS** URL, load online; wait for Available offline and the
   rules preview/effective label. Install from Chrome. Confirm card/rules dates.
2. Search `sol`, `sol ring`, `blood moon`, and `sheold`; check expected cards first,
   symbols, Oracle text and rulings. Back must retain the query.
3. Search `ward`, `deathtouch`, `dies`, `priority`, `layers`, and `702.19`. Open
   glossary/rule details, follow a source reference and a subrule, then go Back.
4. Use New search repeatedly; verify keyboard focus and that only viewed cards
   enter the five-card recent list. Check dark mode and long rules text.
5. Fully close the installed app, enable airplane mode, and cold-launch it. Repeat
   both card and rules searches/details/reference links, including Necropotence.
6. Reconnect after a new complete deployment. Keep the old app usable while it
   downloads; use Update ready · Reload. Verify all data/date labels together.
   Interrupt a subsequent update before completion, then cold-launch offline:
   the previous complete app must still work.
7. Record phone model, OS/Chrome version, power-saving state and warm query p95;
   target <50 ms, with no rules initialization blocking the input thread.

## Future opportunities (not implemented)

Independent player/judge relevance judgments, carefully evaluated vocabulary
expansion, and real-device total-memory/TTI tracking. No broad question-answering
claim should follow from this small retrieval evaluation. Historical snapshot
retention could support old citations, but V1.2 explicitly detects mismatches.

## UI review follow-up

Exact card/face-name queries now give non-exact BM25 rules/glossary matches a
quieter background, normal-weight titles and muted category labels. The exact card
retains its existing presentation. Direct rule-number and exact glossary/section
matches retain their existing emphasis, including card/glossary ambiguity such as
Flash. Prefix queries are unchanged. All results remain visible, in the same order,
with the same tap targets; no result cap, filter, expansion control or routing change
was introduced. This avoids implying that incidental word matches after Blood Moon
have the same relevance as the exact card, without hiding potentially useful text.

Preview rendering remains controlled by the explicitly selected release mode.
Effective-mode regression tests cover result labels, the search status, rule and
glossary headings, and removal of the preview notice. Source URL, effective date,
retrieval timestamp and snapshot identity remain in the Source disclosure. Tests
that previously assumed the selected release must always be a preview now use
explicit fixtures, so a legitimate future effective selection can pass the suite.
The current selection remains preview; it was not activated prematurely.

Verified at desktop and 375px widths, including dark mode and the Flash ambiguity.
Full production tests (38), research tests (5), build, all five evaluation modes,
and production-vs-baseline evaluation passed. All 66 top-ten rankings remain
unchanged; split/prebuilt Hit@5 remains 83.3%. Architecture and features are unchanged.
